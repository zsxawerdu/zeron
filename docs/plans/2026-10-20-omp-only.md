# OMP-only Zeron: architecture, UI, and migration plan

Planning deliverable; no application implementation is included.

Implementation handoff: [ordered work packages, contracts, verification, and next-session prompt](2026-10-20-omp-only-handoff.md). Start there when continuing in a new session; this document remains the architecture and feature-scope reference.

## 1. Product contract

Make Zeron a native application for OMP, not a multi-agent application with OMP added as another option.

- OMP is the sole production agent runtime. No direct Claude Code, Codex, Cursor, Devin, Grok, Hermes, Pi, OpenCode, or Antigravity execution paths remain after cutover.
- Model providers supported by OMP remain available THROUGH OMP. Removing those providers would contradict full OMP support and the supplied model-catalog screenshots.
- OMP owns inference, model routing, credentials, tools, subagents, agent modes, approvals, memory, compaction, and native session history.
- Zeron owns native presentation, windows/tabs, workspace navigation, device attachment, OS integration, and optional application sync. These are not competing agent providers.
- Preserve existing user data. Remove obsolete execution code, not historical conversations or external CLI installations.
- Full support is a release acceptance condition, not a promise that basic RPC chat already provides parity. Every supported-build feature must have an explicit UI/control path and exercised acceptance scenario.
- New OMP releases require compatibility qualification. Dynamic discovery prevents hard-coded omissions, but cannot automatically implement a new interaction model.

## 2. Evidence and baseline

### Current application

The repository is Rust + GPUI, with an engine, typed UI/device RPC, Loro projections, optional remote sync, and an iOS client. ARCHITECTURE.md understates the current harness count and mobile implementation; source takes precedence.

The transcript loss is explicit: parts.rs:406-416 discards output/diff text; sanitize_tool_call at 589-615 strips file and unknown/MCP arguments. Full detail is currently host-journal-only. The redesign needs authorized detail retrieval, not indiscriminate replication of all raw output.

### OMP evidence

Reference screenshots show OMP 18.12.4. Installed executable reports 18.12.5.

Isolated, no-model-prompt smoke checks against 18.12.5 succeeded:

- rpc-ui startup and ready frame; v2 transport negotiation.
- get_state, get_available_commands, get_subagents.
- goal with op=get; get_tree; get_entries; get_available_thinking_levels.
- set_ask_dialog; get_logout_accounts against an empty isolated account store; subagent event subscription.
- Clean exit after closing stdin.
- omp config list --json returned 559 setting descriptors. Inspected enum descriptors had value/type/description, not a complete enum/default/provenance schema.

A first isolated startup with no selected/authenticated model exited with an actionable error before ready. Onboarding must work before a normal session process can start.

The successful probes used a disposable home/config/workspace, an inert credential and loopback endpoint, and sent no inference prompts. They did not validate live approvals, model inference, audio, collaboration, plan review, or the application's rendered UI.

### Documentation drift matters

The website RPC guide is a smaller surface than the upstream protocol reference. Upstream documents goal management, queue edits, session entries/tree/fork, subagent steering/cancellation, logout, prediction, live voice, and session_settled. Several of these were independently observed in the installed build.

Other differences affect behavior: website settings docs describe external changes as generally requiring relaunch; current upstream RPC docs describe config watching and protocol-specific defaults. Do not choose one globally: pin the target runtime/client/schema, then test each live setting and its effective value.

## 3. Architecture decision

Retain the native Rust/GPUI application and replace the multi-harness backend with a dedicated OMP integration.

Preferred boundary: owning Rust engine -> one long-lived `omp --mode rpc-ui` subprocess per independently active session. Retain normal session persistence; `--no-session` is for probes, not product sessions. Viewports attach to the engine, not directly to child stdin.

Use OMP's official `sdk/rust/omp-rpc` client/generated wire types where suitable. Pin the matching source revision; verify packaging and licensing. Its client is blocking: isolate it on dedicated workers, never GPUI or Tokio executor threads. Audit close/drop behavior, Unix process groups, Windows teardown, event buffering, and callback cancellation before adoption. Reuse the wire schema with a thin async transport only if the existing client cannot meet measured requirements; do not create a second protocol interpretation.

Do not default to ACP: it exposes useful Plan/permission/editor workflows, but is not the complete OMP-native UI contract and changes MCP ownership. Do not run ACP and RPC against the same session concurrently. Do not introduce a Bun SDK service merely to wrap an already-supported Rust-to-OMP process boundary.

### Ownership

| State | Authority | Application representation |
| --- | --- | --- |
| Conversation tree, active leaf, model replay metadata, native artifacts | OMP session manager | Indexed/paged projection retaining native IDs and provenance |
| Model/provider/role resolution and credential selection | OMP | Catalog and account views; no duplicated provider implementation |
| Tool execution, approvals, compaction, modes, workers | OMP | Structured events, pending interactions, native controls |
| Pending user delivery before OMP admission | Owning engine | Durable command ledger and offline queue |
| Admitted steering/follow-up work | OMP | Reconciled native queue state, not a second scheduler |
| Windows, tabs, pane sizes, fonts, local shortcuts | Zeron | App-local preferences |
| Device/space registration and optional sync | Zeron | Existing transport with OMP-aware schemas and authorization |

OMP native history is authoritative for agent continuation. Loro remains the viewport/offline-sync projection, not a competing conversation tree. Store engine chat ID, owning device, OMP profile, session ID/path, and active leaf separately. A tab title rename must flow through the appropriate OMP session-name operation, not create a second independent title generator.

### Protocol invariants

- Serialize writes; continuously drain stdout independently of responses and UI callbacks; keep stderr separate.
- Negotiate v2, validate reassembly limits and chunk sequences, and page large histories.
- Track request admission, prompt yield, and session settlement separately. Background work can wake a yielded session; never tear down on the first agent_end.
- Preserve unknown events/roles/content metadata in a versioned local envelope. Render a generic inspection view for unknown presentation, not silent data loss.
- Do not replay opaque provider blocks into a new fabricated conversation. OMP owns replay.
- Correlate approval/ask responses, cancellation, and deadlines. A closed view, timeout, disconnect, or stale answer must never become approval.
- Expose requested versus effective model, reasoning, fast/slow, and tool settings. Unsupported is not the same as off.
- Handle runtime startup/discovery errors, missing models, stale cursors, session_busy, overflow, extension failures, and unexpected exit explicitly.
- Application delivery IDs do not imply OMP-side deduplication. If a crash occurs after admission but before recording the outcome, reconcile native history/state and mark uncertain work; never blindly resend a potentially side-effecting request.
- Native queue removal currently matches text/queue, including first-match semantics for duplicates. Do not invent precise per-item cancellation guarantees without a runtime ID contract.

### Scope and privacy

Keep application local/synced account boundaries distinct from OMP named profiles. Preserve a user's existing OMP setup by default, but never automatically upload its sessions or leak another app profile's projections/artifacts. Remote views address the owning host's profile; local filesystem paths are not portable remote identifiers.

Fetch full tool details/artifacts lazily through the owning engine with access checks. Durable local history and optional encrypted/synced copies need explicit retention and deletion behavior. Secrets, auth tokens, and full-control collaboration links do not belong in ordinary settings snapshots or logs.

## 4. UI structure

Keep the workspace shell, session list, tabs, files, changes, and terminal. Replace the agent selector with an OMP runtime/profile indicator. No generic provider-management layer remains for external agent CLIs.

Primary surfaces:

1. **Conversation**: complete transcript plus composer and runtime status.
2. **Models & roles**: quick session picker and a full persistent model hub.
3. **Plan review**: dedicated document review and execution choices.
4. **Agent hub**: parent/child tree, worker status, transcripts, steering and cancellation.
5. **Session/context inspector**: history tree, memory, compaction, usage, and artifacts.
6. **OMP settings**: searchable full settings catalog and integration management.

Secondary inspectors: jobs/processes, tools/MCP/extensions, approvals, browser/computer state, review/security results, collaboration, audio, and runtime diagnostics. These should not all become permanent sidebar items.

### Screenshot mapping

- Compact picker: searchable available models, recent choices, role shortcuts, current selection, and session-only apply.
- Full hub: Roles / All models / OMP providers; modality filters; capability/context/output/pricing details; measured speed and intelligence metadata only when supplied, with absent/stale data shown honestly.
- Role assignment: arbitrary discovered/custom roles, explicit versus automatic resolution, thinking, cycle order, fallback chains, global/project scope, clear assignment versus reset.
- Composer: text and image attachments, file/URI mentions, slash/skill/MCP commands, model, reasoning, fast/slow capability, mode, working directory/branch, context/usage, send/steer/follow-up/stop. Drafts survive navigation and rejected sends.
- Thinking controls: reasoning level changes computation; hide/expand/prose-only controls change presentation. Do not conflate them with omitting model context.
- Appearance: map OMP semantic colors to the native theme system; support light/dark selection, accessibility, transcript options, and symbols where relevant. Keep app fonts/window layout separate. Terminal-specific settings stay available for the terminal surface rather than pretending to affect GPUI.
- Settings: readable labeled categories, search, modified-state marker, scope and effective-value/source, reset-to-default versus remove-override, and live/restart-required feedback.

Do not hard-code screenshot model names, catalog counts, role counts, or theme defaults.

Conversely, an advertised command name does not prove all its TUI subcommands work in RPC.

## 6. Full-parity blockers and decisions

### Native plan review

Highest-priority feasibility gate. Need OMP-owned mode transitions, read-only enforcement, draft/revision state, annotations, execution model selection, all approval/context-transfer choices, cancellation, and resumed state. A prompt saying 'please plan' or `--plan-yolo` is not equivalent.

Preferred closure: expose existing OMP behavior through a maintained/versioned upstream RPC host contract. A supported extension is acceptable only if it invokes the actual underlying behavior. Do not fork planning policy into Zeron. If upstream access cannot be obtained, this remains a named blocker to full native parity, not a feature silently deferred past completion.

### Settings and role writes

Reuse OMP validation/persistence; no direct credential DB writes. Global config CLI commands do not automatically implement project writes or session-only changes. Native settings service must know scope, effective value, supported values, defaults, secret status, and apply/restart semantics. Reset writes a default; removing an override restores inheritance. Prove config watching on the chosen version rather than forcing restarts or claiming every change is live.

### Approvals and authentication

Use rpc-ui with extension/tool UI enabled. Implement real approval decisions with original target/details, timeout and cancellation. Remove the hard-coded auto-approve behavior; show effective policy at session creation without silently weakening existing user choices. MCP auth challenges and secret OAuth prompts need supported host flows or a clearly identified OMP authentication terminal until a secure bridge exists.

### Arbitrary terminal extensions

Built-in OMP workflows should be native. Third-party extensions can create arbitrary TUI components that cannot be serialized into GPUI today. Provide a clearly named OMP terminal surface for terminal-only customization if needed; it is not a substitute for native built-in features. Same-session handoff requires settlement, flush, release, exact resume, and exclusive ownership. A terminal merely opening beside the app does not prove safe handoff.

If the acceptance requirement is every third-party TUI rendered natively with no terminal surface, OMP needs a portable UI protocol; that cannot honestly be promised from existing RPC.

### Protocol defaults and lifecycle

Current upstream docs note protocol-specific defaults for memory/advisor/task/async behavior and rpc-ui disabling PTY by default. Compare interactive and hosted effective settings and behavior. Surface differences and expose deliberate choices; do not force all defaults merely to make controls appear enabled. Goal continuation in RPC requires its specific setting. Background work and supervised jobs need explicit lifetime policy separate from tab closure.

### Remote and mobile

Apply the same runtime protocol and permissions through the owning engine. Remote approval response races must settle once. Never record audio on the remote host when the user expects the local phone microphone. OMP collaboration guests have narrower rights than trusted Zeron device peers; retain these as separate authorization classes.

## 7. Migration sequence and exit gates

These are implementation milestones, not reduced-scope releases.

| Phase | Work | Exit gate |
| --- | --- | --- |
| 0. Contract qualification | Pin OMP binary/source/wire/client; enumerate commands/settings/tools/modes; probe live approvals, settings, plan, subagents, persistence, PTY, voice and collab; design missing upstream contracts | Every capability classified as proven native API, supported command/CLI, terminal-specific compatibility, or explicit blocker with closure. Decide full-plan feasibility before broad UI work. |
| 1. OMP runtime core | Dedicated supervisor, official Rust client integration, callbacks, v2, native session binding, host tool/URI bridge, model discovery, lifecycle and crash reconciliation | Real OMP conversation survives UI detach/reconnect and process resume; no token/event loss or duplicate submission; no forced approval bypass. |
| 2. State and history | Rich event schema, native session identity/tree, unknown-field preservation, paged details/artifacts, approvals, queues, phases, usage, settings scope | Local and remote viewers can inspect original tool detail, answer requests, and recover persisted history correctly. |
| 3. Everyday native UI | Composer, transcript, quick picker, model/role hub, settings, onboarding/auth, full tool cards, context inspector | Screenshot workflows operate end-to-end against real OMP; role assignment differs correctly from session switching. |
| 4. Advanced OMP surfaces | Complete Plan Review, goal/vibe/advisor/prewalk/loops, Agent Hub, memory/compaction, skills/MCP/plugins, browser/debug/review/security/media | All ledger workflows use OMP behavior; stop/cancel/approval and capability-disabled cases exercised. |
| 5. Remote/mobile and parity | Shared bindings/Swift surfaces, OMP collaboration, remote artifacts, audio routing, terminal-extension compatibility, platform lifecycle | Desktop and retained mobile/remote clients have explicit complete coverage; permission and profile isolation hold under reconnect. |
| 6. Clean cutover | Remove non-OMP adapters/catalogs/accounts/installers/defaults, obsolete generic selection, old delegation/title orchestration, tests/docs/scripts/CI tied to removed runtimes | Product has one runtime path; legacy data remains readable/exportable; no production fallback to another agent. |

Migrate legacy conversations as read-only archives with provider provenance unless OMP provides a verified native import for that source. Offer explicit continuation into a NEW OMP session from reviewed context where necessary; do not relabel another runtime's opaque session ID as resumable OMP history. Keep migration readers isolated from active runtime contracts.

Preserve user-installed external CLIs and credentials. Do not uninstall or delete them as part of code removal. Existing OMP sessions should appear without copying/replaying their conversation into a different session.

The same removal rule applies to direct voice-provider paths and packaged/discovered Codex voice helpers. Preserve reusable capture/playback and call UI where suitable, but model-backed voice must use OMP. Existing remote audio transport is not proof that OMP supports client-owned audio.

Update desktop/headless/mobile wire versions together. Reject incompatible active clients clearly; do not let old clients submit removed harness requests. Keep legacy archive decoding separate from live execution compatibility.

## 8. Acceptance suite

The release gate is a versioned capability ledger with observed outcomes on each retained platform, not a count of implemented screens.

Required scenario families:

1. Fresh installation with no authenticated model: useful onboarding before session ready; login, model selection, first turn, and actionable startup errors.
2. Existing OMP profile: discover models/roles/extensions/MCP/history; preserve scopes and credentials; no automatic data upload.
3. Model workflows: session-only switch versus global/project assignment, automatic/custom roles, unsupported thinking, fallback/revert, quota and disabled providers.
4. Streaming: text/reasoning/tool updates/multiple assistant messages/unknown blocks; image-only results; large outputs over v2 and paged history.
5. Approvals/questions: allow/deny/cancel/timeout, multi-select/free-text/editor details, concurrent viewers, disconnect and stale replies; no implicit approval.
6. Queues: steer versus follow-up, same-text messages, attachments, promotion/removal, abort/restore, rejected admission and crash uncertainty.
7. Lifecycle: background jobs after yield, goal continuation, session_settled, window/tab close, engine crash, graceful shutdown, OS-specific child process cleanup.
8. Plan: read-only investigation, pause/resume, refine, annotations, all three execute-context choices, save without execute, keep-context eligibility, mode conflicts and cancellation.
9. Agents: nested workers, subscription resume, full transcripts, steering/cancel, supported revival, isolation/worktree results, failures and usage attribution.
10. Sessions: exact resume, tree branch versus fork, native artifacts, compaction/snapcompact/handoff, rename/pin/move/delete/export/share and legacy archive migration.
11. Settings: effective versus saved value, all scopes, reset versus inherit, invalid input, secret masking, concurrent saves, live apply versus restart, new unknown keys.
12. Integrations: MCP auth/prompts/resources, extension UI/cancellation/reload, mounted host tools/URIs, browser/computer safety, LSP/DAP, GitHub/review/security.
13. Media: local dictation/TTS/live voice start-mute-stop and device permission failures; local versus remote capture routing; generated images and large attachments.
14. Collaboration: host/control/view-only rights, first answer wins, reconnect/resync, link secrecy and revocation; no privilege inheritance from app device sync.
15. Platform and scale: long transcripts, many agents, offline/slow remote detail fetch, bounded memory, UI-thread responsiveness, macOS/Windows/Linux and retained iOS behavior.

Use deterministic protocol fixtures for transport/state invariants and real OMP smoke scenarios for behavior. Actual rendered native surfaces need visual/interactivity checks. Source inspection and mock replies cannot certify UI parity.
